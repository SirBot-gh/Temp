# Design Plan: `Sanitize-DeviceState.ps1`

PowerShell script that takes a PAN-OS **device state** bundle, sanitizes the XML
configuration files inside it, and writes each one back out as a `.txt` file with
the content otherwise unchanged.

This document is the build spec. Everything Cursor needs is here; the only external
reference is the sibling script `Split-PanBundle.ps1` in this repo, whose
`$RedactElements` list must be reused verbatim (see §4.1).

---

## 1. Goal and non-goals

**Goal**

1. Accept a device state bundle (`.tar` / `.tgz` / `.tar.gz`) *or* an already-extracted
   folder.
2. For every `*.xml` file inside, replace the text of known secret-bearing elements
   with the literal string `REDACTED`.
3. Write the result to an output folder with the same relative path and the
   extension changed from `.xml` to `.txt`. **No transformation of the data** beyond
   redaction: the output is still well-formed XML text, just named `.txt` so it can be
   uploaded to tools that reject `.xml`.
4. Emit a manifest and a post-write verification that proves no secret survived.

**Non-goals**

- No parsing/splitting of the config into fragments (that is `Split-PanBundle.ps1`).
- No reformatting, pretty-printing, or re-indenting of the XML.
- No conversion to JSON/CSV/anything else.
- No handling of non-XML files other than listing them as skipped.

## 2. What a device state bundle looks like

Per Palo Alto's docs, **Export device state** bundles "the running configuration"
plus "device group and template settings pushed from Panorama", and for a
GlobalProtect portal also certificate and satellite information. The bundle is a
gzip'd tar (`device_state_cfg.tgz`, generated on-box under
`/opt/pancfg/mgmt/device-state/`, or generated by Panorama with
`save device-state device <serial>` / `scp export device-state device <serial>`).

### 2.1 Standalone firewall (observed in `device_state_cfg.tar`)

```
device_state_cfg.tar
├── running-config.xml        # full local config; contains <phash> for every admin
├── certificate_info.xml      # GP portal certs; empty <vsys/> shell when not a portal
├── satellite_info.xml        # GP LSVPN satellites; empty shell when not a portal
├── knob-setting.xml          # debug knobs; no secrets
├── device_blacklist.xml      # usually empty
├── sp/                       # EMPTY on a standalone box
└── template/                 # EMPTY on a standalone box
```

### 2.2 Panorama-managed firewall (the audit targets)

`sp/` and `template/` mirror the on-box directories `/opt/pancfg/mgmt/sp/` and
`/opt/pancfg/mgmt/template/`. The file names below are the ones that appear in
PAN-OS commit/error logs for those directories; they are the **expected** names but
the script must not depend on them (see 2.4):

```
device_state_cfg.tgz
├── running-config.xml                    # local config (merged local settings)
├── certificate_info.xml
├── satellite_info.xml
├── knob-setting.xml
├── device_blacklist.xml
├── sp/                                   # "shared policy" = Panorama DEVICE GROUP push
│   └── vsys1/                            # one folder per vsys (vsys1..vsysN)
│       ├── pretrans-sp-config.xml        # device-group config as received from Panorama
│       └── sp-config.xml                 # post-transform device-group config (may or may not be present)
└── template/                             # Panorama TEMPLATE / template-stack push
    ├── pretrans-template-config.xml      # template config as received from Panorama
    └── template-config.xml               # post-transform template config (may or may not be present)
```

What lives where, so the sanitizer and the manifest can label it:

| Path | Role (reuse `Classify-PanXml` from `Split-PanBundle.ps1`) | Secret exposure |
|------|------|------|
| `running-config.xml` | `local-config` | admin `phash`, local auth profiles, SNMP, local IKE PSKs |
| `template/*.xml` | `pushed-template` | device/network settings from Panorama: LDAP/RADIUS/TACACS secrets, SNMP communities, IKE PSKs, syslog/HTTP profile passwords, certificates/private keys, admin accounts pushed via template |
| `sp/vsys*/*.xml` | `pushed-device-group` | pre/post rulebases and objects; secrets are rare but possible (e.g. external dynamic list credentials, data-filtering patterns) |
| `certificate_info.xml`, `satellite_info.xml` | `other` | certificate material when the box is a GP portal |
| `knob-setting.xml`, `device_blacklist.xml` | `other` | none |

### 2.3 Related artifacts the script should also accept

These are not device state exports but show up in the same engagements and contain
the same kinds of data. Because the script is filename-agnostic (2.4) they work
without special-casing; list them in the README so assessors know they're supported:

- **Tech-support file** `opt/pancfg/mgmt/saved-configs/.merged-running-config.xml`
  (note the leading dot) — the Panorama + local config merged into one document.
  Palo Alto's own recovery KB points at this file. The `*.xml` filter must match
  dot-files (it does on Windows; on PowerShell 7 on macOS/Linux pass `-Force` to
  `Get-ChildItem`).
- **Panorama "Export Panorama and devices config bundle"** — a `.tgz` containing
  `running-config.xml` for Panorama itself plus one `<serial>_import.tgz` or
  per-device XML per managed firewall. Nested archives must be extracted one level
  (add a rule: if an extracted file is itself `.tgz/.tar`, extract it in place into a
  folder of the same base name and continue enumerating).

### 2.4 Rules the implementation must follow

- **Never use a filename allow-list.** Enumerate every `*.xml` recursively under the
  extraction root and sanitize all of them. Exact names of pushed files vary by
  PAN-OS version and by vsys count; missing one means leaking a Panorama-pushed
  RADIUS secret.
- **Classify by content, not name**, using the same logic as
  `Split-PanBundle.ps1 → Classify-PanXml` (root `<template>` → pushed-template;
  device-group markers without `<deviceconfig>` → pushed-device-group; `<config>`
  with `<deviceconfig>` → local-config; else `other`). Record the role in the
  manifest so the assessor can see a Panorama-managed box actually produced
  template and device-group files. **Warn loudly** in the summary if the bundle has
  `sp/` or `template/` folders but zero XML inside them — that usually means the
  export was taken from a box that isn't in sync with Panorama, and the audit would
  be incomplete.
- Files may have **leading whitespace/tabs before the root element** and a
  `<?xml version="1.0"?>` declaration. Both must be preserved.
- Preserve sub-paths (`sp\vsys1\pretrans-sp-config.txt`). Never flatten: multi-vsys
  boxes produce identically named files in different folders.
- Real bundles can be several MB; `running-config.xml` alone can be 10–50 MB on a
  busy firewall, and `pretrans-template-config.xml` on a large template stack is
  similar. Avoid O(n²) string work; one parse + one write per file.
- Secrets in the sample: 3 × `<phash>` in `running-config.xml`. Real
  Panorama-managed bundles add SNMP communities, LDAP bind passwords,
  RADIUS/TACACS secrets, IKE pre-shared keys, private keys, API keys, etc. —
  mostly in the **template** file, which is why `template/` is the most important
  folder to get right. The element list in §4.1 covers these.

## 3. CLI contract

```powershell
.\Sanitize-DeviceState.ps1 -InputPath <file-or-folder> -OutputRoot <folder>
                           [-MaskIdentity] [-Force] [-WhatIf] [-Verbose]
```

| Parameter        | Type     | Required | Meaning |
|------------------|----------|----------|---------|
| `-InputPath`     | string   | yes      | Path to a `.tar`/`.tgz`/`.tar.gz` bundle **or** a folder that already contains the extracted files. Accept multiple bundles via a folder containing several archives (process each). |
| `-OutputRoot`    | string   | yes      | Folder to write sanitized `.txt` files into. One subfolder per bundle, named after the bundle file (minus extension) or the input folder name. |
| `-MaskIdentity`  | switch   | no       | Additionally mask hostname, serial numbers, and IPv4/IPv6 addresses (see §4.2). Off by default because identity is usually needed for the assessment; on when the output leaves the customer boundary. |
| `-Force`         | switch   | no       | Overwrite an existing output subfolder. Without it, refuse and exit non-zero if the target subfolder already exists (prevents stale/mixed output). |
| `-WhatIf`        | switch   | no       | Standard `SupportsShouldProcess`; list what would be written, write nothing. |

Exit codes: `0` success, `1` usage/input error, `2` verification failed (a secret
pattern was found in output — output folder is deleted), `3` one or more XML files
failed to parse (see §5 fail-closed rule).

**Compatibility:** must run on **Windows PowerShell 5.1** (default on customer
Windows boxes) *and* PowerShell 7+. No PS7-only syntax (`??`, ternary, `-Parallel`,
`ForEach-Object -Parallel`). `Set-StrictMode -Version Latest` and
`$ErrorActionPreference = 'Stop'` at the top.

## 4. Sanitization rules

### 4.1 Tier 1 — secret material (always on)

XML-aware replacement using `System.Xml.XmlDocument`. For each element whose
**local name** exactly matches one of the names below, set `InnerText = 'REDACTED'`
(only if it currently has non-empty text). Match on local name so a namespace prefix
cannot bypass the rule. Exact match, not substring — `<password-complexity>` and
`<password-profile>` must **not** be touched.

Reuse this list **verbatim** from `Split-PanBundle.ps1` (`$RedactElements`) so both
tools redact identically; if one list grows, grow the other:

```
phash, password, private-key, public-key, preshared-key, bind-password, secret,
api-key, auth-password, priv-password, community, shared-secret, client-key,
master-key, snmp-community-string, authpwd, privpwd
```

Implementation sketch:

```powershell
$xpath = ($RedactElements | ForEach-Object { "//*[local-name()='$_']" }) -join ' | '
foreach ($n in $doc.SelectNodes($xpath)) {
    if ($n.InnerText.Length -gt 0) { $n.InnerText = 'REDACTED'; $count++ }
}
```

Also redact **attributes** with those names (rare in PAN-OS but cheap to cover):
`//@*[local-name()='password' or ...]`.

### 4.2 Tier 2 — identity (only with `-MaskIdentity`) — OPTIONAL, build last

**Not required for the initial deliverable.** The assessment needs usernames, IPs,
hostnames, and zone/rule names intact; only secret values are redacted. Build
Tier 1 (§4.1) and the safety-net pass (§4.3) first and ship; implement this switch only if time permits (it exists
for the case where output must leave the customer boundary). If skipped, keep the
parameter reserved (not implemented -> exit 1 with a clear message) so the CLI
contract is stable.

Applied after Tier 1, on the same `XmlDocument`:

| Target | Rule | Replacement |
|--------|------|-------------|
| Hostname | element local-name `hostname` | `HOST-REDACTED` |
| Serial | element local-name `serial`, `serial-number` | `SERIAL-REDACTED` |
| IPv4 (any text node or attribute value) | regex `\b(?:\d{1,3}\.){3}\d{1,3}(?:/\d{1,2})?\b` | `10.0.0.0` keeping any `/nn` suffix, so the XML remains valid for PAN-OS schema tools |
| IPv6 | regex for `[0-9a-f:]{3,}` containing `::` or ≥2 colons, with optional `/nn` | `fd00::1` + suffix |

Walk all text nodes and attribute values (`//text() | //@*`) for the regexes so
`<entry name="10.10.20.1/24"/>` is caught too. Do **not** touch `netmask` values
(`255.255.255.0` is not sensitive and changing it breaks readability); exclude
elements whose local name is `netmask` from the IPv4 pass.

### 4.3 Safety-net regex pass (always on, runs on the final text)

After the XML is serialized to a string and before it is written, run these regexes
on the raw text and replace matches with `REDACTED`. This catches secrets that live
in elements not on the list (unknown/new PAN-OS fields) and anything that XML parsing
might have missed:

| Pattern | What it catches |
|---------|-----------------|
| `\$[156]\$[^\s<]{1,120}` | crypt-style password hashes (`$1$`, `$5$`, `$6$`) |
| `-----BEGIN [A-Z ]+-----[\s\S]*?-----END [A-Z ]+-----` | PEM private keys / certs |
| `(?i)(?<=<[^>]*(?:key|secret|passw)[^>]*>)[^<]{8,}` | text inside any element whose name contains `key`/`secret`/`passw` that survived Tier 1 |

Count these separately in the manifest as `safety_net_hits`. A non-zero value on a
real bundle means the Tier 1 list has a gap and should be reported.

## 5. Processing pipeline

```
for each bundle (or the single input folder):
  1. Resolve input
     - if file: require extension in .tar/.tgz/.tar.gz; else exit 1
     - if folder: use as-is
  2. Extract (archives only)
     - use tar.exe (ships with Windows 10 1803+ / Server 2019+); fall back to
       error with a clear message if tar.exe is missing
     - extract into a TEMP dir: Join-Path $env:TEMP "sds_<guid>"
     - NEVER extract into OutputRoot. Raw files must not land next to output.
  3. Enumerate
     - Get-ChildItem -Recurse -File -Filter *.xml (case-insensitive)
     - record non-XML files as "skipped" in the manifest; do not copy them
  4. Per XML file
     a. read bytes -> detect BOM -> read as UTF-8 string
     b. $doc = New-Object System.Xml.XmlDocument; $doc.PreserveWhitespace = $true
        $doc.LoadXml($text)
        - on parse failure: record file as FAILED, do not emit anything for it,
          continue; final exit code becomes 3  (fail-closed: never write an
          unsanitized file just because the parser choked)
     c. Tier 1 redaction (and Tier 2 if -MaskIdentity)
     d. serialize: use XmlWriter with
          OmitXmlDeclaration = $false, Indent = $false, Encoding = UTF8 (no BOM),
          NewLineHandling = None
        so whitespace/declaration come out as they went in
     e. safety-net regex pass on the serialized string
     f. compute output path:
          relative = path relative to extraction root
          outFile  = Join-Path $bundleOut ([IO.Path]::ChangeExtension($relative, '.txt'))
        e.g. running-config.xml -> running-config.txt
             template\t1.xml     -> template\t1.txt
     g. create parent dir; write with [IO.File]::WriteAllText(path, text, UTF8-no-BOM)
     h. SHA256 of the written file; append manifest row
  5. Verification (hard gate)
     - re-read every written .txt and scan with the §4.3 regexes plus the
       Tier 1 element-name XPath (re-parse) looking for any non-REDACTED text
     - any hit -> delete the whole bundle output folder, print the offending
       file and line number, exit 2
  6. Manifest
     - write <bundleOut>\MANIFEST.txt (human-readable) and MANIFEST.json
     - fields per file: source relative path, output relative path, role
       (local-config | pushed-template | pushed-device-group | other), bytes in,
       bytes out, tier1_redacted_values, tier2_masked_values, safety_net_hits,
       sha256, status (OK | FAILED | SKIPPED)
     - header: script version, timestamp (UTC), input path, MaskIdentity on/off,
       totals, exit status
  7. Cleanup
     - Remove-Item the TEMP extraction dir in a finally{} block, always,
       even on error
```

Output layout example for the sample bundle:

```
<OutputRoot>\device_state_cfg\
    running-config.txt
    certificate_info.txt
    satellite_info.txt
    knob-setting.txt
    device_blacklist.txt
    MANIFEST.txt
    MANIFEST.json
```

(`sp/` and `template/` are not created when they contain no XML.)

Panorama-managed example:

```
<OutputRoot>\FW-EDGE-01_device_state\
    running-config.txt
    certificate_info.txt
    satellite_info.txt
    knob-setting.txt
    device_blacklist.txt
    sp\vsys1\pretrans-sp-config.txt
    template\pretrans-template-config.txt
    MANIFEST.txt
    MANIFEST.json
```

## 6. Code organization

Single file, ~300–400 lines, functions in this order:

| Function | Responsibility |
|----------|----------------|
| `Resolve-InputBundles` | turn `-InputPath` into a list of `{Name, Kind=Archive|Folder, Path}` |
| `Expand-Bundle` | `tar.exe -xf` into temp dir; returns the dir |
| `Read-XmlText` | BOM-aware read to string |
| `Invoke-Tier1Redaction` | `[XmlDocument]` in, count out |
| `Invoke-Tier2Masking` | `[XmlDocument]` in, count out (only if switch) |
| `ConvertTo-XmlString` | XmlWriter serialization honoring preserved whitespace |
| `Invoke-SafetyNet` | regex pass on string, returns `{Text, Hits}` |
| `Test-OutputClean` | verification gate over written files |
| `Write-Manifest` | txt + json |
| `main` block | parameter validation, loop, exit code |

Constants at the top of the file, clearly commented:
`$ScriptVersion`, `$RedactElements`, `$IdentityElements`, `$SafetyNetPatterns`,
`$OutputExtension = '.txt'`.

Use `Write-Verbose` for per-file progress and `Write-Host` only for the final summary
and the "never upload the raw bundle" reminder (matching the tone of
`Split-PanBundle.ps1`).

## 7. Edge cases to handle explicitly

- **Archive contains a top-level folder** (some exports wrap everything in
  `device_state/`): compute relative paths from the extraction root, so the output
  mirrors whatever was inside. Do not try to strip a wrapper folder.
- **Duplicate base names in different sub-paths** (`template\a.xml` and `sp\a.xml`):
  fine, because sub-path is preserved. Never flatten.
- **Empty XML file** (0 bytes): treat as FAILED parse, do not emit.
- **Element on the redact list that is a container** with child elements (e.g. a
  future `<secret><value>..</value></secret>`): `InnerText = 'REDACTED'` would
  flatten the children — that is acceptable and safer; count it and move on.
- **CRLF vs LF**: preserve whatever the input had (`NewLineHandling = None`).
- **Filename case**: `RUNNING-CONFIG.XML` must still be matched; output keeps the
  original case of the base name.
- **`-InputPath` pointing at `OutputRoot`** or a child of it: refuse, exit 1.
- **Long paths on Windows**: prefix with `\\?\` only if a path exceeds 259 chars;
  otherwise leave alone (keeps 5.1 happy).

## 8. Test plan

Use the sample `device_state_cfg.tar` as the fixture (copy it to
`tests\fixtures\device_state_cfg.tar`). Add a second fixture by hand-editing a copy
of `running-config.xml` to include:

- an `<snmp-community-string>CANARY-COMMUNITY</snmp-community-string>`
- a `<bind-password>CANARY-BIND</bind-password>`
- a `<preshared-key><key>CANARY-PSK</key></preshared-key>` (container case)
- a stray `$6$abc$CANARYHASH` inside an element **not** on the list (safety-net case)
- a PEM block inside `<certificate>`
- a `template\pretrans-template-config.xml` (root `<template>`, containing a
  `<bind-password>CANARY-LDAP</bind-password>` and an
  `<snmp-community-string>CANARY-SNMP</snmp-community-string>`) and a
  `sp\vsys1\pretrans-sp-config.xml` (device-group with a pre-rulebase) to exercise
  the Panorama-managed layout, recursion, and content classification; plus one
  non-XML file (`foo.log`) to exercise skip logic
- the repo's existing `TESTFW-01_device_state.tgz` (synthetic names
  `pushed_template.xml` / `pushed_devicegroup.xml`) as a third fixture to prove the
  script does not depend on file names
- one deliberately malformed `broken.xml`

Expected results on the **original sample**:

| Check | Expected |
|-------|----------|
| Output files | exactly 5 × `.txt` + 2 manifests |
| `running-config.txt` tier1 count | 3 |
| all other files tier1 count | 0 |
| `safety_net_hits` everywhere | 0 |
| `grep -c 'REDACTED' running-config.txt` | 3 |
| `grep '\$5\$' running-config.txt` | no match |
| `<hostname>PA-VM</hostname>` present | yes (no `-MaskIdentity`) |
| *(only if Tier 2 was built)* with `-MaskIdentity`: `PA-VM`, `10.10.10.10`, `10.10.20.1` absent; `255.255.255.0` present | yes |
| byte-for-byte diff of `knob-setting.txt` vs `knob-setting.xml` | identical |
| exit code | 0 |
| temp extraction dir | removed |

Expected on the **canary fixture**: every `CANARY-*` string absent from output,
manifest roles show exactly one `local-config`, one `pushed-template`, one
`pushed-device-group`; output contains `sp\vsys1\pretrans-sp-config.txt` and
`template\pretrans-template-config.txt`;
`safety_net_hits = 1` for the stray hash, `broken.xml` listed as FAILED with no
`broken.txt` emitted, `foo.log` listed as SKIPPED, exit code 3.

Negative test: temporarily comment out one element from `$RedactElements`, run the
canary fixture, confirm exit code 2 and that the output folder was removed.

Write these as a `tests\Run-Tests.ps1` using plain assertions (no Pester dependency
required, though Pester is fine if already present on the build machine).
